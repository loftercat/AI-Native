# 概念定义与划分标准（concepts-guide）

> **目的：知识普及**。让所有参与者（产品 / 研发 / 测试 / AI Agent）对「用户旅程」与「业务场景」有一致理解，并知道**分几条旅程、几个阶段、几个场景**的判定标准。
> 定义均引自官方权威来源（文末 §6 依据表），本仓库裁剪处已注明。

---

## 1. 官方权威定义

### 1.1 用户旅程（User Journey / Journey Map）

**NN/g（Nielsen Norman Group）定义原文**：

> "A journey map is a visualization of the process that a person goes through in order to accomplish a goal."
> （旅程图 = 对**一个人为达成一个目标**所经历过程的可视化呈现。——《Journey Mapping 101》，Sarah Gibbons，2018）

豆包解释：
用户旅程：特定角色为达成某一业务目标，从触发起点到终态（目标完成或放弃）的全过程路径，按时间划分为若干阶段，记录各阶段的行为、触点与遇到的问题（想法与情绪可选）；




标准结构为两条轴：

| 轴 | 内容 |
|----|------|
| **横轴（时间线）** | 高层次**旅程阶段（Phases）**按时间铺开，如 discover → try → buy → use → seek support |
| **纵轴（泳道）** | 每阶段下的用户行为（Actions）、想法（Mindsets）、情绪曲线（Emotions）、机会点（Opportunities） |

**本仓库裁剪**：JSD 旅程表以「用户行为 / 系统响应 / 触点 / 断点」替代情绪泳道（后端仓库关注系统侧），横轴语义不变。

### 1.2 业务场景（Scenario）

两个权威来源，指同一粒度：

**UML / 用例工程（Cockburn）**：

> "Scenario — a complete sequence of steps through the whole use case."
> （场景 = 贯穿整个用例的**一条完整步骤序列**——即用例的一条执行路径。）

**BDD / Cucumber 官方（Gherkin Reference）**：

> "This is a concrete example that illustrates a business rule. It consists of a list of steps."
> （场景 = **说明一条业务规则的具体示例**，由一组步骤构成；建议每个示例 **3–5 步**。）

**本仓库定义**（综合上述）：业务场景 = 旅程某阶段在特定条件下的**确定响应路径**，结构恒定为「前置条件 + 触发 + 用户可见的预期结果」，分**主 / 备选 / 异常**三型（对应 UML 的主成功场景 + 备选流 + 异常流）。

豆包解释：用户旅程中某阶段，满足特定前提，用户做一个操作后，系统对应的一条确定走向（正常 / 分支 / 失败）。

## 2. 两者关系：嵌套，不是并列

```text
用户旅程（宏观容器：一条目标链）
 ├─ 阶段 J1.1 ──┬─ 场景 SC-J1-01（主）
 │              ├─ 场景 SC-J1-02（备选）   ← 场景（微观切片：粒度最小、细节最深）
 │              └─ 场景 SC-J1-03（异常）
 └─ 阶段 J1.2 ──── 场景 SC-J1-04…
```

一句话：**旅程管广度（横着走，路径不缺环），场景管深度（竖着切，每步不缺分支）**。NN/g 对 journey 与 flow 的定位同构：journey 是 holistic high-level，具体交互是 "deep dive into specific areas of the high-level user journey"。

## 3. 用户旅程的划分标准

### 3.1 要分几条旅程

| 规则 | 依据 |
|------|------|
| **1 个角色 × 1 个目标 = 1 条旅程** | NN/g："Provide one point of view per map"——每张旅程图只承载单一视角；覆盖两类用户须做两张图 |
| Epic 内数量指引：**1 条主旅程 + 0～3 条次要旅程** | 主旅程 = 本 Epic 目标闭环那条；次要旅程 = 同 Epic 附带交付的旁路（如主链路之外的代客预约） |
| 超过 3 条次要旅程 → 疑似 Epic 边界过宽 | 呼应 STORY §5：Epic 判定标准之一是规模可控（5～15 张 Story） |

### 3.2 每条旅程要分几个阶段

| 规则 | 依据 |
|------|------|
| 阶段 = 用户可观测的**状态跃迁**，用动词短语命名（找车场 → 选车位 → 下单支付 → 拿到凭证） | NN/g 示例即五阶段动词链（discover → try → buy → use → seek support） |
| 数量指引：**每条旅程 4～8 个阶段** | 少于 3 个：旅程本身不成立（没有过程）；多于 10 个：优先怀疑阶段太细应合并，其次怀疑该拆两条旅程 |
| 判定一个阶段成立的问句：「用户此刻想完成的事，和上一步是同一件事吗？」 | 相邻阶段须有明确交接物（如「选好车位」是「下单支付」的输入） |

## 4. 业务场景的划分标准

### 4.1 要分几个场景

| 规则 | 依据 |
|------|------|
| **每个阶段 ≥1 主场景**（通常恰好 1 条） | UML：每个用例恰有一条主成功场景 |
| 备选场景（同一目标的合法替代手段）：每阶段 0～3 条 | UML 备选流：值得写的才写 |
| **异常场景：每个对外能力 ≥1 条**，按 [scenario-branch-checklist.md](./scenario-branch-checklist.md) 逐维度扫描产出 | UML 异常流；BDD「一条 Rule 用一个或多个 Scenario 从不同角度说明」 |
| 每阶段合计 **3～10 条**；超过 10 条 → 检查阶段是否太粗（该拆阶段）或混入了另一能力 | 数量超限是粒度信号，不是错误本身 |
| 每条场景 **3～5 个步骤**（前置 / 触发 / 结果不宜再展开超过两层） | Gherkin 官方："we recommend 3-5 steps per example" |

### 4.2 停止标准（什么时候不用再挖）

- 场景的预期结果**可判定**（写得出具体用户可见表现：文案 / 状态 / 去向）→ 停；
- 写不出 → 不是继续编，而是转入 JSD §6 开放问题或 `[AI推断]`；
- 分支清单必扫维度已扫完且无新命中 → 停。

### 4.3 因子组合法：场景的第二个来源（B 端经典「人货场」；可选）

旅程竖切产生「同一阶段的异常/备选分支」；**因子组合**产生「跨阶段的业务规则变体」。因子 = 使业务规则发生变化的正交维度，B 端经典分解框架为「人货场」：人（角色）× 货（业务对象）× 场（渠道/时段/情境）；同族方法有 JTBD（情境触发任务）与测试界的正交/成对组合（用于剪枝）。

| 规则 | 说明 |
|------|------|
| **差异驱动** | 仅当组合的业务规则不同才立场景（本仓库示例：企业账户包月 与 车主临时 的计费/审批规则不同 → 各立场景）；规则相同的组合合并 |
| **代表组合** | 组合数 > 20 时剪枝：每个因子取值至少被一个场景覆盖，其余组合不展开 |
| **覆盖度** | 因子表非空时，每个因子取值 ≥ 1 场景覆盖（并入 JSD 覆盖度自检） |
| **数量影响** | 因子派生场景计入每阶段 3～10 的配额；持续超限 → 因子定义过细，先收敛因子取值 |
| **适用边界** | **可选**：C 端简单旅程（单角色、单业务对象）不必套用；B 端 / 多变化维度业务建议必做 |

## 5. 示例：从有缺陷的描述到合格的 JSD（教学案例）

> 通用示例（数据管线域，非本仓库业务，展示方法可迁移）。**读法**：先看 5.1 的原始描述，尝试自己找问题，再看 5.2 诊断与 5.3 修订——这是初学者最高频的四类偏差。

### 5.1 原始描述（缺陷版）

> 项目里有一个「样本筛选和发布」功能。用户旅程有 2 个：①筛选训练样本，发布任务；②查看历史发布的任务。旅程 1 有 2 个阶段：筛选、发布。筛选对应的业务场景——前置条件：打开 xx 页面，选择样本的分类和标签；触发：点击筛选按钮；预期结果：显示筛选的结果。

### 5.2 逐层诊断

| # | 层 | 问题 | 校准 | 依据 |
|---|----|------|------|------|
| 1 | 旅程 | 旅程 1 命名像功能清单（两个动词并列） | 以终态目标命名：「筛选并发布训练样本任务」 | 旅程 = 角色达成目标的路径，名字应说清终点 |
| 2 | 旅程 | 未确认筛选的独立性 | 若存在「只筛不发」的用户（纯查样本库）→ 拆两条旅程；若筛选只服务发布 → 合一条 | 1 角色 × 1 目标 = 1 条旅程 |
| 3 | 阶段 | 2 个阶段疑似缺环 | 断点走查：筛完能直接发布吗？要不要「预览/确认」？发布后在哪看「成功/失败」？→ 常见结果为 4 阶段 | 断点走查是旅程层的核心动作，缺环在此层暴露成本最低 |
| 4 | 场景 | 前置条件混入用户动作 | 「选择分类和标签」是 When；前置写**状态**（已登录、页面已加载、库有数据） | 前置 = 状态，触发 = 动作 |
| 5 | 场景 | **一个阶段只配一个场景（= 只写 happy path）** | 每阶段竖切：主 1 条 + 异常若干（无匹配 / 条件非法 / 超大结果） | 每对外能力 ≥1 异常场景；每阶段合计 3～10 |

### 5.3 修订后的 JSD 片段（合格版）

旅程表（J1 节选）：

| 阶段编号 | 阶段 | 用户行为 | 系统响应 | 断点/痛点 |
|----------|------|----------|----------|-----------|
| J1.1 | 筛选 | 选分类和标签，点筛选 | 返回命中样本列表（含总数） | 结果超大时如何加载？ |
| J1.2 | 确认 | 预览命中样本、确认数量 | 展示选中样本摘要 | 误筛大集合直接发布的事故在此设防 |
| J1.3 | 发布 | 点击发布 | 创建发布任务（异步） | 任务失败用户在哪看到？ |
| J1.4 | 查看结果 | 查看任务状态 | 返回发布结果与日志 | — |

场景矩阵（J1.1 竖切——示范**一个阶段展开成多个场景**）：

| 编号 | 所属阶段 | 类型 | 前置条件 | 触发 | 预期结果（用户可见） |
|------|----------|------|----------|------|----------------------|
| SC-J1-01 | J1.1 | 主 | 已打开筛选页，样本库有数据 | 选分类和标签，点击筛选 | 显示命中样本列表，含总数 |
| SC-J1-02 | J1.1 | 异常 | 同上 | 组合条件无命中 | 显示「未找到符合条件的样本」，提供清空筛选入口 |
| SC-J1-03 | J1.1 | 异常 | 已打开筛选页 | 未选任何条件直接点筛选 | 提示「请先选择筛选条件」 |
| SC-J1-04 | J1.1 | 异常 | 命中结果超大 | 点击筛选 | 分页/限量加载，给出总数提示 |

### 5.4 教学要点

1. 三层各管一件事，不越位：**旅程**答「谁、从哪到哪」，**阶段**答「路过哪几站」，**场景**答「每一站遇到 X 会怎样」；
2. 阶段层做**断点走查**（缺环在此暴露），场景层做**分支扫描**（异常在此补全）——两把不同的尺子；
3. 「前置 = 状态，触发 = 动作，预期结果 = 用户可见表现」，三者写混是最高频错误（见诊断 #4）；
4. 一个阶段展开成多个场景是常态；**一个阶段只有一个场景 ≈ 只写 happy path**（见诊断 #5）。

## 6. 术语防混淆：同词不同义（资料冲突的根源）

网上资料互相矛盾，多数因为 "scenario" 在不同流派里差着一个数量级：

| 流派 | 他们说的 "scenario" | 换算到本仓库术语 |
|------|---------------------|------------------|
| Cooper 目标导向设计 | context scenario：persona 达成目标的**叙事描述** | ≈ 文字版用户旅程 |
| NN/g 旅程图 | 旅程图头部的 scenario：**情境设定**（谁、在什么处境、带着什么期望） | ≈ 旅程的背景信息 |
| UML / RUP | 用例内的**一条执行路径** | ≈ 本仓库的业务场景（同粒度） |
| BDD / Cucumber | 单条验收示例（Given-When-Then） | ≈ 本仓库的业务场景（同粒度） |

看到「先写 scenario」的资料，先分清它指哪一列再判断对错。本仓库 JSD 中的「场景」**始终指最细粒度**（UML/BDD 列）。
