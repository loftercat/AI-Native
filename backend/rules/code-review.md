# 代码审查规则（编码后、合并前的质量门禁）

> **规范听 Rule，流程听 Skill**：本规则定义何时送审、审什么、分级、报告格式与闭环口径；编码流程见 [feature-coding](../skills/feature-coding/SKILL.md)，缺陷修复见 [bugfix](../skills/bugfix/SKILL.md)；前端线有独立的代码审查规则（见 frontend 线，本规则不依赖前端路径）。
> 设计为**最小闭环**：一个审查点、一页报告、独立上下文；不引入多门审查与成本度量；重审上限见 §五。
> 同源版本：v1（2026-11-12）；修改 P0–P3 表、闭环门槛、报告 footer 或轮次上限时，必须同步前端线代码审查规则。

## 一、何时送审

- **触发点**：
  - `feature-coding`：Step 7 `mvn test` 通过后、Step 8 独立代码审查（实现汇总/commit 前）；
  - `bugfix`：Step 6 验证通过后、Step 7 修复报告/合并前；
  - `frontend-feature-coding`：步骤 6 验证通过后、联调/提测前；
  - `integration-test-design`：新增/修改 `*IT` / `*ScenarioIT` 后、合入前（按 §二 定档：通常 L1/L2；>8 文件/diff >400 行或含业务代码/跨模块 → L3）；
  - `api-blackbox-test` / `test-data-design`：生成/修改 pytest 或 seed 脚本后、合入前（按 §二 定档：通常 L1/L2；>8 文件/diff >400 行或含业务代码/跨模块 → L3；只审脚本，不审验收用例/DP 正文）。
- **不送审**：L0 改动（纯注释、格式化、重命名、日志/文案字符串）。在回复中说明跳过原因，用户可否决。
- **审查通过前禁止 commit / push**（与全局工作纪律一致）。
- `legacy-test-migration` 只产分类矩阵与 TS-LEGACY 规格，不产代码，不送审；其下游生成的测试代码由对应 Skill 的审查触发。
- **审查人**：独立上下文（独立 AI 会话 / 审查 agent / 人），不复用实现会话；不绑定特定 Agent 工具。

## 二、档位选择

| 档位 | 适用改动 | 审查深度 | 闭环门槛 |
|------|----------|----------|----------|
| **L1 轻审** | ≤2 文件的小增量：新增函数/字段/日志/校验、不改既有分支逻辑、非核心链路；单个配置常量的值调整 | 只查正确性：空值/边界、明显逻辑错误、异常被吞、资源泄漏、明显安全问题 | P0/P1 必须修；P2 记录不阻塞（最多 1–2 条）；P3 不报 |
| **L2 标准**（默认） | 3–8 文件，或单模块内的逻辑变更 | 完整流程；按改动背景与关注点逐条回应 | P0/P1/P2 必须修；P3 酌情 |
| **L3 深审** | 核心链路（支付/资金/订单/鉴权/权限/事务/并发/幂等）、DDL/批量数据订正、跨模块、>8 文件或 diff >400 行 | 完整流程 + 专项清单：事务边界/回滚、幂等、并发、兼容性、权限、数据迁移 | P0–P3 全部闭环 + 复审确认 |

- **对外协议 / 设备报文 / 接口契约**不得用 L1。
- 仅测试/脚本代码（IT、pytest、seed）按 §二 定档：通常 L1/L2；>8 文件/diff >400 行或含业务代码/跨模块 → L3。
- 实际改动明显超出所报档位（如标 L1 却动了支付主流程）→ 审查人立即指出并按更高档审查。
- 未注明档位时按 **L2** 执行。

## 三、送审输入（缺一不可）

| # | 输入 | 说明 |
|---|------|------|
| 1 | 审查档位 | L1 / L2 / L3 |
| 2 | 改动背景 | Story / Bug 编号、AC/BR、需求约束、不能破坏的行为 |
| 3 | 审查范围 | `git diff HEAD` + `git status` 中的**本次相关**新增未跟踪文件；或 `<base>..HEAD`；列出重点文件，排除无关历史报告/临时文件 |
| 4 | 上游工件 | Story、DD、TS、OpenAPI/schema 路径（有则给） |
| 5 | 测试结果 | `mvn test` / 前端测试结果；哪些 AC 已覆盖 |
| 6 | 关注点 | 本次最担心的 3–5 项（分层、事务、幂等、错误码、契约等） |

> 只给 diff 不给背景和工件，审查人只能做通用扫描，审不出 AC 追溯与契约问题。
> 未指定范围时审查人才看全部未提交改动；发起审查时以显式列出的文件为准，不扩大到无关未跟踪文件。

**审查任务书（跨 Agent 通用）**（复制后替换占位）：

```text
审查档位：L2
规则：先读 rules/code-review.md（§二 档位 / §四 审查清单 / §五 P0–P3 与闭环）
改动背景：STORY-... / BUG-...；AC/BR：...；不能破坏：...
审查范围：git diff HEAD + git status 新增文件（本次相关；排除历史报告/临时文件；重点：...）
上游工件：Story ...；DD ...；TS ...；OpenAPI ...
测试结果：mvn test ... 通过；覆盖 AC-...
关注点：...
只读：不修改仓库文件、不落盘报告
输出：按 P0–P3 附 path:line；按 templates/code-review-report.md 的六行格式输出档位、P0–P3 计数与结论（报告由实现者落盘）
```

> 这份任务书就是跨 Agent 的接口：任何独立审查人只要能读仓库并按此输出即可，不需要特定 Agent 或插件。

## 四、审什么

### 4.1 通用清单

1. **正确性**：空值/边界、状态机、异常路径、资源泄漏、并发/幂等。
2. **AC → 测试 → 实现追溯**：每条 AC 是否有测试和实现对应；测试是否断言用户可见结果，而不是只断言内部调用。
3. **分层与边界**：BFF/域/基础设施职责；是否有越界（BFF 写状态机、`*-impl` 写 Controller、跨域直调 Mapper 等）。
4. **异常与错误码**：`BizException`/`ErrorCode` 号段、失败文案与 OpenAPI 一致。
5. **事务与数据**：事务边界、失败回滚、条件更新、软删、SQL/索引、Mapper XML。
6. **契约一致性**：OpenAPI/schema 与实现一致；契约语义变更是否回 `detail-design`。
7. **测试质量**：无 `@Disabled` / 删断言 / 跳过；命名与断言可追溯到 AC。
8. **安全与权限**：入口鉴权、数据归属校验、敏感字段/日志泄漏。
9. **可维护性**：重复代码、命名、复杂度（P3 酌情）。

### 4.2 场景附加

| 场景 | 额外重点 |
|------|----------|
| `feature-coding` | 按 [implementation-checklist.md](../skills/feature-coding/references/implementation-checklist.md) 抽查；AC 追溯、分层、事务、OpenAPI 同步 |
| `bugfix` | 最小 diff、根因是否修掉、回归影响、公共代码改动、是否引入新分支 |
| `frontend-feature-coding` | operationId 范围、字段只认 OpenAPI、页面不直接发请求、请求层/错误码、页面状态机、错误展示、`setData`/性能、`onUnload` 清理 |
| `integration-test-design` | 测试真实性（真实 HTTP/真实 DB、只 Mock 外部系统）、Mock 边界、稳定性/隔离、数据清理 |
| `api-blackbox-test` / `test-data-design` | pytest/seed 脚本：Token/URL 不硬编码、不接生产、`seed_key` 幂等、清理脚本、失败输出可定位 |

## 五、分级与闭环

| 级别 | 含义 | 处理 |
|------|------|------|
| **P0** | 会产生错误结果、丢数据、安全漏洞 | 必须修 |
| **P1** | 特定条件下出错、边界未处理、资源泄漏 | 必须修 |
| **P2** | 性能问题、明显设计缺陷、异常处理缺失 | L1 记录；L2/L3 必须修 |
| **P3** | 命名、重复代码、可读性 | L1 不报；L2 酌情；L3 闭环 |

- **L1**：P0/P1 清零；P2 记录不阻塞（最多 1–2 条）；P3 不报。
- **L2**：P0/P1/P2 清零；P3 酌情。
- **L3**：P0–P3 全部闭环 + 复审确认。
- **BB/SEED 脚本即使判 L1**，§4.2 的 QA 重点（不接生产、Token/URL 不硬编码、`seed_key` 幂等、清理脚本存在且反序、与 IT/TS 去重）按 **P1** 处理，必须清零。
- **外部验证 P2**（设备实测、第三方确认等）：标「待确认」，写明验证方式，不阻塞；但必须在报告和提交说明中记录。
- 审查人**只读**，不修代码；实现者修复后重派，报告同名覆盖、轮次 +1。连续 >3 轮仍不通过 → 交还人工（与 `bugfix` 的 >3 轮上限一致），不要无限重试。

## 六、报告

- **落点**：`docs/reviews/{迭代}/REVIEW-CODE-{阶段}-{Story编号或Bug编号}-{slug}.md`
  - 功能实现：`REVIEW-CODE-IMPL-STORY-2026-S03-001-query-allocate-space.md`
  - 集成测试：`REVIEW-CODE-IT-STORY-2026-S03-001-query-allocate-space.md`
  - 缺陷修复：`REVIEW-CODE-FIX-BUG-2026-001-search-empty.md`
  - 前端实现：`REVIEW-CODE-FE-STORY-FE-2026-S03-001-destination-search.md`
  - 黑盒脚本：`REVIEW-CODE-BB-STORY-2026-S03-001-query-allocate-space.md`
  - 造数脚本：`REVIEW-CODE-SEED-STORY-2026-S03-001-query-allocate-space.md`
  - **同一 Story 的实现审查、IT 审查、黑盒/造数审查必须分文件**，避免后一阶段覆盖前一阶段报告。
- **模板**：[code-review-report.md](../templates/code-review-report.md)
- **固定 footer**（由实现者/主流程按审查人输出落盘）：

  ```text
  - 审查档位：L2
  - P0：0
  - P1：0
  - P2：0
  - P3：0
  - 结论：通过
  ```

- **结论「通过」** = 该档位闭环门槛满足；否则「不通过」。
- **重审**覆盖同名报告文件，轮次记在头部字段；历史轮次不另存。
- 审查人只读；**报告由实现者（主流程）落盘**，不要要求审查人写文件。

## 七、与 Story 审查的区别

| 维度 | Story 审查 | 代码审查 |
|------|------------|----------|
| 时机 | 拆卡后、详设前 | 编码后、合并前 |
| 对象 | Story 卡（AC/BR/拓扑/模块归属） | 代码 diff（实现/测试/契约） |
| 分级 | Blocker/Major/Minor | P0–P3 |
| 报告 | `REVIEW-STORY-*` | `REVIEW-CODE-*` |
| 门禁 | 状态「已确认」时机器强制 | 当前为流程门禁；机器门禁后续 |
| 审查人 | 独立 AI/人 | 独立 AI 会话 / 审查 agent / 人 |

> 两者不能互相替代：Story 审查发生在代码之前，代码审查发生在代码之后。

## 八、跨 Agent 落地（不绑定工具）

本规则只要求审查人满足三个条件：**独立上下文、只读、能读取仓库与 diff**。不要求特定 Agent、插件或平台。

| 形态 | 落地方式 |
|------|----------|
| 独立 AI 会话 | 新开会话，粘贴 §三 的审查任务书；要求只读、按 P0–P3 输出 |
| 专用审查 Agent | 传入同一任务书；要求只读、不修改文件、按 P0–P3 输出 |
| 人 | 按 §四 清单审查，按 §六 报告 |
| CI / 静态分析 | 跑 lint、OpenAPI diff、测试作为机械层；语义审查仍由 AI 或人承担 |

- **接入项目**：把本规则、报告模板与 `templates/` 一起随线分发；在项目 `AGENTS.md` 增加「代码审查」节，供任意 Agent/审查人读取。目标布局示例：规则 → `rules/code-review.md`，模板 → `templates/code-review-report.md`；`AGENTS.md` 里的链接按目标布局调整。
- **不需要**安装特定 Agent；报告由实现者（主流程）按审查人输出落盘。
- **前端线**：使用前端线自带的代码审查规则与报告模板（与后端同源、前端重点见 §4.2）；不要跨线引用后端路径。
