# 定时任务高可靠设计实践指南（Java 微服务）

> **L1 静态层上下文资产**：`detail-design` 步骤 6 在 AC/BR 出现批处理、对账、调度、定时清理、超时扫描等关键词时加载本指南。
> **微服务多实例要求**：每个领域微服务各自运行自身的定时任务，**禁止**将所有任务集中在单一启动模块；微服务默认多副本部署，**必须设计防重叠执行方案**（具体调度与分布式锁框架见 [system-landscape.md](../architecture/system-landscape.md) §5.4 **E-6**，未定则详设阻断）。

## 一、定时任务的核心挑战

| 问题 | 后果 |
|------|------|
| 任务重叠执行 | 多实例 / 多 Pod 同时跑同一 cron → 重复推进状态、重复扣减或释放资源 |
| 执行失败无追溯 | 静默漏处理直到人工发现数据不一致 |
| 长任务中断 | 进程重启后从头扫 → 重复处理或漏处理 |
| 不可观测 | 不知是否执行、耗时、成功/失败条数 |

## 三、设计原则

### 原则 1：防重叠（同一时刻只有一个实例执行，微服务必守）

微服务默认多副本部署，**禁止以「单实例可接受」跳过防重叠设计**；具体方案按画像 §5.4 **E-6** 选型：

| 方案（画像 E-6 备选） | 说明 |
|------|------|
| **ShedLock（JDBC / Redis）** | 轻量注解式分布式锁，适合轻量 `@Scheduled` |
| **DB 分布式锁表** | 基于本服务独立数据库，不额外引入中间件 |
| **XXL-JOB / K8s CronJob** | 独立调度中心或容器层统一调度，适合大量任务统一管控与重试 |

要点：锁过期时间 / `lockAtMostFor` 须大于任务最长执行时间（建议预期耗时 × 2），获锁失败直接 skip 并打 INFO 日志，不抛业务异常。

### 原则 2：支持失败重试与可观测

- 建议本服务维护独立的任务执行记录表（`scheduler_execution`），记录 `task_name`、`status`、`started_at`、`finished_at`、`retry_count`、`processed_count`、`failed_count`、`error_message`。
- 关键日志统一携带 `task`、`elapsedMs`、`processed`、`failed`，连续失败达到阈值触发告警。

### 原则 3：分批扫描 + 游标推进 + 单条幂等

- 禁止一次性 `SELECT` 全表加载所有待处理记录；采用固定 batch（如 100–500 条）分批推进。
- 单条业务处理必须幂等（见 [idempotency-guide.md](./idempotency-guide.md) 方案 D 状态条件更新），确保失败重跑安全。
- 单条失败不中断整批：记录失败明细后继续下一条，批次结束后汇总。

## 四、微服务分层落点

```text
{service}-impl       各领域微服务独立启用调度入口（按画像 §5.4 E-6）
  ├── app/scheduler/ 薄入口：触发适配 + 分布式锁防重 + 委托 Job
  ├── app/job/       编排：分批游标、执行记录、单条异常隔离与重试
  ├── app/service/   单条业务状态机与幂等写库（本服务独立 DB）
  └── app/client/    如需通知或调用下游微服务，经远程契约调用（按画像 P-2）
```

**禁止**：
- 在 BFF 服务中写定时/批处理触发入口
- 在调度入口类内堆砌核心状态机大段逻辑（应下沉到 Service 便于单测）
- 定时任务跨服务直连他服务数据库表
