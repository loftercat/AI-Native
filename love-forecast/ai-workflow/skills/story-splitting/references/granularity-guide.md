# Story 粒度指引

> 配套 `story-splitting` Skill。冲突时以 Skill 流程 + `rules/story-ac-conventions.md` 为准。

## 1. 粒度公式

```text
一张 Story = 一个角色（或同质角色组）× 一个完整业务意图 × 一个风险域
```

| 维度 | 何时拆 |
|------|--------|
| **角色** | 权限模型、可操作范围不同 |
| **业务意图** | 无法用一句「作为…我想…以便…」说清 |
| **风险域** | 资金、权限、合规、状态机、第三方依赖不同质 |

**拆分优先级**（多维度冲突）：**风险/权限 → 角色/场景 → 流程步骤 → CRUD**（仅简单管理类）。

> **注意**：上表是「怎么切卡」，不是 Story **序号/交付先后**。卡号顺序见 Skill §5.6 与下文 §9。

## 2. 禁止作为拆分维度

- HTTP 方法（GET/POST 各一张）
- DAO / Service / 技术分层
- 正常流与异常流拆成两张 Story（异常写进 AC）
- PRD 步骤号 1:1 映射成 Story

## 3. 管道型 Epic

同一角色、同一意图、一次确认后的「保存 → 打包 → 调外部 → 展示结果」= **一条用户旅程**，默认 **2 张 Story**：

| 卡 | 内容 |
|----|------|
| 准备 | 入口、权限、表单、前置校验 |
| 提交（含结果） | 确认后的连续动作 + 同次流程内的结果展示/状态查询 |

**禁止**把 submit 与 show-result、换 token、调接口拆成多张独立 Story（除非「发布历史」等独立入口的第三旅程）。

## 4. 微服务 / BFF 类 Story 注意

| 信号 | 建议 |
|------|------|
| 横跨 BFF + 多服务 | 按**可独立验收的价值**拆，不是按技术层拆 |
| 仅改 DTO 字段 | 可与相关 API Story 合并，若 AC≤6 |
| 外部 smart-parking 集成 | 单独 Story，标明集成边界 |

## 5. 粒度快查表

| 信号 | 动作 |
|------|------|
| 不同权限/风险域、独立状态机、AC>10 且场景异质、一句用户故事说不清 | **继续拆** |
| 严格串行且无法单独演示价值、保存/打包/调接口管道步骤、像 Task（AC≤2 仅技术动作）、单旅程却 ≥4 张 | **必须合并** |
| 同角色同流程、共享 BR、无独立高风险、合并后 AC≤6 可一次验收 | **可以合并**（须全部满足） |

**INVEST · Small**：一个迭代内可**独立验收**的业务切片，不是「几天写完的代码量」。

## 6. 复杂度与字段裁剪

| 复杂度 | 必填字段 |
|--------|----------|
| **简单** | 用户故事、范围、AC |
| **中等** | + BR、依赖、校验职责（谁校验：BFF/领域服务/前端） |
| **高复杂** | + 业务价值详述、测试关注点、DoD、风险说明 |

**先看风险再看功能大小**——涉及资金/权限/合规一律按高复杂处理。

## 7. 原型对齐检查

> 细则见 Skill §5.4。有 Axure 导出 HTML 时，**每张 Story 落盘前**对主原型页过一遍。

对原型页每条产品标注标四类：**本 Story AC** / **后续 Story** / **前端另仓** / **显式非目标**。

| 原型内容类型 | 通常落点 |
|--------------|----------|
| 地图默认定位、控件样式 | 前端另仓 |
| 列表/详情展示字段（含地址、**费率说明**） | 本 Story AC 或后续 Story（须在 §5 写清） |
| 点击后的下单/支付 | 后续 Story（管道「提交」卡） |
| Admin 配置项 | 后续 Story + 链 HLD 配置 Story |

**管道「准备」卡**：除 query/allocate 外，检查「选车场后用户还需看到什么」（收费预览、规则摘要等）是否已有 AC 或显式 defer。

## 8. AC 完备性（落盘前）

> 细则见 [ac-completeness-checklist.md](./ac-completeness-checklist.md) 与 Skill §5.5。

- 异常/边界 **写在同一张 Story 的 AC**，不另拆 Story（§2）
- 含失败语义的 **BR 须有对应失败 AC**；§2.3 校验职责须在 AC/BR 可验收
- **产品 BR**（用户可见）与 **实现 BR**（算法，须 `[AI推断]` + §8）须区分
- **查询类**须覆盖：无匹配、关键词非法、含多余空格匹配（AC）
- 单 Story AC 建议 ≤12；超过且场景异质 → 评估拆卡（§5）

## 9. 依赖拓扑与编号（Epic / 批量原型）

> 细则见 Skill §5.6、[sprint-index-template.md](../templates/sprint-index-template.md)。

| 原则 | 说明 |
|------|------|
| 先 DAG 后序号 | 批量原型须先旅程地图 + 阻塞依赖图，再赋 `STORY-{迭代}-{序号}` |
| 序号 = 拓扑序 | 阻塞依赖 `A → B` ⇒ `序号(A) < 序号(B)` |
| Foundation 最早 | 骨架、鉴权、主数据、Mock 适配层占 W0，序号早于业务卡 |
| 两类依赖 | **阻塞依赖**（缺了验不过）vs **消费方**（本卡产出被用；勿反向写阻塞） |
| 禁止编号依据 | 原型页码、HLD `S-xx`、PRD 章节、模块名 |

**反例**：按 Axure 页面顺序把「搜索分配」编为 001、「主数据配置」编为 020——应为主数据 W0 在前、搜索 W1 在后。
