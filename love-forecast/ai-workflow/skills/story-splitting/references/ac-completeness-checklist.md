# AC 完备性检查清单

> 配套 `story-splitting` Skill §5.5。**落盘前必做**；与原型对齐检查（§5.4）互补——§5.4 防漏原型能力，本清单防漏异常/边界验收。

## 1. 原则

| 原则 | 说明 |
|------|------|
| **异常进 AC，不进新 Story** | 正常流与失败流在同一张 Story；见 granularity-guide §2 |
| **用户可见须可验** | 会影响 `message`、列表为空、字段缺失等用户/API 消费方可见结果的规则，须有 AC（或显式标「后续 Story」） |
| **§2.3 须有着落** | 「校验职责」表中 BFF/领域写的职责，须在 AC 或 BR 中有对应条目，禁止只写职责不写验收 |
| **可合并，不可省略** | 同类参数校验可合并为一条 AC（When 列举多种输入）；不可因「详设再写」而静默省略 |
| **控制粒度** | 单 Story AC 建议 ≤12；超过且场景异质时考虑拆卡（见 granularity-guide §5） |

## 2. 必查维度（按 Story 类型勾选）

落盘前对每张 Story 过下表。**命中行须有条目**——写入 AC、BR，或在 §2.2 / §5 写明 defer 依据。

### 2.1 通用（所有含 HTTP/API 的 Story）

| 维度 | 检查问题 | 落盘要求 |
|------|----------|----------|
| **主成功路径** | 每个对外能力是否至少 1 条成功 AC？ | 每条 API/用户意图 ≥1 成功 AC |
| **BR 失败语义** | 每条含「否则不可 / 须 / 禁止 / 仅当」的 BR 是否有失败 AC？ | 每条此类 BR ≥1 失败 AC，或引用上游 `STORY-xxx.BRn` 且本卡有对应 When |
| **资源不存在** | 按 ID 查询/操作时，目标不存在如何响应？ | 失败 AC + 具体 `message` |
| **权限/鉴权** | BFF 有鉴权时，未登录/无权限如何响应？ | 失败 AC；集成边界可写「依赖 iam-server，本 Story 验 Filter 拒绝」 |
| **参数格式** | §2.3 写 BFF 校验的参数，非法时如何响应？ | 失败 AC + 具体 `message`；见 §3 |

### 2.2 查询 / 搜索类（含关键词、列表、筛选）

| 维度 | 检查问题 | 落盘要求 |
|------|----------|----------|
| **无匹配** | 合法输入但业务无结果？ | 失败或空结果 AC + 具体 `message`（与「参数非法」区分） |
| **关键词为空** | `keyword` 等必填搜索参数缺失、空串、仅空白？ | 失败 AC + 具体 `message` |
| **输入规范化** | 首尾空格、连续空白是否影响匹配？ | **BR** 写规范化规则 + **AC** 举至少 1 个带多余空格的 When（如 `华润  大厦`） |
| **未开放/不可用** | 资源存在但业务上不可用（如 `bookingEnabled=false`）？ | 与「不存在」区分文案的失败 AC |

### 2.3 写操作 / 状态变更类

| 维度 | 检查问题 | 落盘要求 |
|------|----------|----------|
| **前置条件不满足** | 状态机、库存、时段等不满足？ | 每条独立失败语义 ≥1 AC |
| **幂等/重复** | 重复提交、重复回调？ | 有则写 BR + AC；无则 §2.2 标非目标 |
| **并发冲突** | 多人争用同一资源？ | 本 Story 边界内写 AC；超出边界写 §6 测试关注点 + defer |

### 2.4 时段 / 金额类

| 维度 | 检查问题 | 落盘要求 |
|------|----------|----------|
| **时间区间** | `end ≤ start`、越界营业时间？ | 每种独立 `message` ≥1 AC |
| **金额/费率** | 缺失配置、计算边界？ | 成功 AC 含关键字段；缺失时失败 AC 或 BR 约定默认 |

## 3. 参数校验 AC 写法

**禁止**只在 §2.3 写「参数非空」而无 AC。

推荐合并为一条失败 AC（示例）：

```markdown
### AC-0x：搜索关键词非法（影响层：BFF）

- **Given** 车主已登录
- **When** 调用 `GET .../lots`，且 `keyword` 为以下任一种：缺失、空串 `""`、仅空白 `"   "`
- **Then** `message` 为 **「请输入目的地或大厦名称」**
```

输入规范化：**产品意图用 AC**；**默认算法用 §8 `[AI推断]`**（示例）：

```markdown
| BR-0x | 搜索关键词规范化处理后，须能与车场名称/地址完成模糊匹配；不得仅因首尾或连续空白导致漏匹配 | 产品意图；见 AC-11 |

### AC-0x：关键词含多余空格仍可匹配（影响层：BFF、inventory）

- **Given** 存在车场名称「华润置地大厦E座」且 `bookingEnabled=true`
- **When** `keyword=华润  大厦`（含连续空格）
- **Then** 返回含该车场的列表；与 `keyword=华润大厦` 的匹配结果一致

## 8. AI 推断项（节选）

| 项 | 推断内容 | 依据 |
|----|----------|------|
| 关键词匹配算法 | `[AI推断]` 首尾 trim + 合并连续空白 + 分词 AND | AC-11 默认实现；详设可替换，不得违背 AC |
```

> **禁止**在 BR 正文写死「分词 AND」等算法且备注无 `[AI推断]`。

## 4. 与缺口三分法的关系

| 类型 | 本清单相关示例 |
|------|----------------|
| **阻断** | 失败文案在原型/Epic 中冲突；是否规范化会改变产品语义 |
| **可补充** | 排序规则、匹配算法、次要字段默认值——**§8 `[AI推断]`**；主路径 AC 仍须完整 |
| **提醒** | 并发、性能——可写 §6 测试关注点，但**不替代**用户可见失败的 AC |

**不再默认 defer 到详设**：必填校验、BR 失败语义、用户可见匹配结果（AC）须在 Story 落盘；**算法细节** 详设默认 + §8 `[AI推断]`。

## 5. 落盘前自检表（复制勾选）

```text
[ ] 每个 API/能力有 ≥1 成功 AC
[ ] 每条含失败语义的 BR 有对应失败 AC（或引用上游且本卡有 When）
[ ] §2.3 BFF 校验职责在 AC/BR 中有对应条目
[ ] 查询类：无匹配 / 关键词非法 / 含多余空格匹配（AC）已覆盖
[ ] 实现类 BR（算法/格式）备注列有 `[AI推断]` 且 §8 有对应行
[ ] 按 ID 操作：不存在 vs 不可用 文案已区分
[ ] 鉴权 Story：未授权路径有 AC（或 §2.2 写明由网关统一处理）
[ ] 未覆盖项已在 §2.2、§5 或 §8 写明 defer 依据
[ ] AC 总数 ≤12 或已评估需拆卡
```
